# 检索与项目参考

1. 从请求提取问题、实体、场景和时间要求。跨项目时仅读取解决问题所需的当前项目信息，不自动上传仓库。
2. status 看绑定和覆盖。首次无索引先 sync；已有索引按更新需要有界刷新，不每次全库扫描。
3. search 使用 2—3 种有意义的表达；中文支持分词与双字组合，英文保留单词。CLI 的 --query 可重复，多个表达合并排序。
4. 检查 matchType、excerpts 和 neighbors。命中收藏理由时引用 captureNote；仅标题命中时可以列出处，正文摘录只引用实际命中的段落。链接邻居另说明进一步阅读的理由。
5. 对相关资料用 fetch 取正文。飞书文档在线核对账号与范围；外部收藏返回 mode=local-source，说明采集时间 fetchedAt、覆盖 coverage 和获取方式 sourceNote。link_only 表示只存了链接和备注。用户明确接受缓存时可 search --offline 或 fetch --offline 读取外部收藏。
6. 根据正文语义、证据质量、场景适配和时效重新排序。第一版没有 embedding 模型，不把 BM25 分数称为语义置信度。
7. 不足时补关键词、沿引用读取或继续 sync；达到合理预算仍不足则报告实际覆盖和缺口。搜索无命中不等于库内绝对不存在。

回答使用项目参考模板：可复用、要调整／不适用、依据、缺口。引用真实 URL；没有真实 block ID 时不编造段落锚点。需要某个视频的原话时核对实际字幕和时间点。

知识库结论是参考；当前项目的事实优先。不能因为旧笔记写过某个方案就替用户修改代码。默认不把回答写回知识库，也不把私人关键词发送到互联网搜索。

用户要求餐厅、零食、好物或随机推荐时按 [personal-records.md](personal-records.md) 进行条目级检索、原文和条件核对，分别给“我的知识库推荐／网上新推荐”。联网只用必要公开条件，不上传个人清单；没有对应品牌／规格／热量依据时不能当已核实候选，随机在核对后的候选池进行，不用BM25第一条冒充抽取。
